# Engineering Insights

1. After the first prompt, identify the modules it concerns. Inspect only what you need to resolve unclear ownership. Before substantive work or an answer about any module, read its `INSIGHTS.md` in full. Repeat when the scope expands to another module.
2. Use `client/INSIGHTS.md`, `server/INSIGHTS.md`, `reviewer-core/INSIGHTS.md`, or `e2e/INSIGHTS.md` for the corresponding package. Use `server/src/modules/repo-intel/INSIGHTS.md` for indexing lessons and the server file for broader server behavior. For a cross-module finding, use the file of the module that owns the behavior. Read the root `INSIGHTS.md` if present and relevant to repository-wide infrastructure. Create it only when recording the first such finding.
3. Keep candidates in the session context as you work. Before the final response, look for verified user corrections, failed approaches, unexpected test results, and reasons behind non-obvious decisions. Keep findings that would change a future decision or prevent repeat investigation and are hard to infer from a routine reading of the code. For `What Doesn't Work`, record the conditions under which the approach failed and what showed it failed.
4. Reread each existing target file in full immediately before updating it. Compare candidates by meaning across all sections and within the batch. If the relevant conditions and takeaway are already covered, skip the candidate. If a new condition, version, or exception changes the recommended action, append only that refinement and reference the earlier entry. For a confirmed contradiction, append a dated correction that identifies the earlier entry by date and subject. For an unresolved contradiction, use `Open Questions` and record the evidence and the next check. Leave files untouched when there are no qualifying entries. If a new finding cannot be saved in the current mode, report it with its target path.
5. Append each qualifying entry at the end of its section as `- YYYY-MM-DD — <condition or symptom>. <reusable action or conclusion>. <evidence>.` Preserve existing entries. For code or tests, cite the repository-relative path and the relevant symbol or test name. For reproduction, include the command and the observed result. For documentation, link to the relevant section.
6. Use these level-two headings in order: `What Works` for verified approaches, `What Doesn't Work` for verified dead ends, `Codebase Patterns` for local conventions and decisions with their rationale, `Tool & Library Notes` for tool and dependency behavior, `Recurring Errors & Fixes` for repeat failures and proven fixes, `Session Notes` for dated summaries that add context, and `Open Questions` for unresolved issues with what is known and the next check.
