## 1. Збереження вартості агента

- Додати nullable `agent_runs.cost_usd` за зразком інших сум у схемі. Без значення за замовчуванням. Існуючі рядки після міграції мають `null`. Зберігати число в USD з точністю від провайдера чи оцінки, округлювати лише для відображення.
- Перевіряти ціну на рівні кожної модельної спроби. OpenRouter використовує кінцеве невід’ємне `usage.cost`, включно з нулем. Якщо його немає, оцінюємо лише цю спробу з повних даних про використання. OpenAI оцінює за наявності повних даних про токени. Якщо бодай одну спробу неможливо оцінити, повна сума агента дорівнює `null`. Зберегти наявне поширення `null` між частинами рев’ю в рушії. Помилки SDK без даних про використання не дають суми.
- Забрати `costUsd` з результату рушія до запису рев’ю та findings. Якщо наступний крок впаде, шлях помилки має зберегти вже обчислену повну суму. Якщо рушій перервався до повернення підсумку, залишити `null`. Суми окремих спроб після перерваного запуску не відновлюємо.
- Читати вартість з одного рядка запуску для обох представлень. `RunSummary.cost_usd` має значення або `null`. Для `RunTrace.stats.cost_usd` під час читання додати канонічну суму до JSON трасування. Пов’язати читання трасування з робочим простором запуску. Старі траси мають відкриватися з `null`.

## 2. Група запусків і вибір останньої команди

- Використати `multi_agent_runs` як персистентний запис однієї команди рев’ю. Кожен виклик `ReviewService.runReview` створює групу, включно з одиночним рев’ю. Додати nullable зв’язок `agent_runs.multi_agent_run_id`. Створювати групу й усі її дочірні запуски в одній короткій транзакції до старту фонового виконання. Прив’язка за ідентифікатором відокремлює одночасні команди для одного PR. Відсутність зв’язку в старих даних не потребує відновлення історії.
- Додати явний час остаточного запису запуску, наприклад `settled_at`. Успішний або аварійний шлях фіксує статус, суму, трасування й остаточний час перед сповіщенням клієнта. Під час скасування ціна вважається очікуваною, поки виконавець не запише фінальний стан. Скасований запуск зберігає статус `cancelled`, навіть якщо останній модельний виклик повернув повну суму під час зупинки. Розширити відновлення після перезапуску на всі осиротілі групові запуски без остаточного запису, включно з уже позначеними `cancelled`. Відновлення фіксує вже збережену суму або `null`, щоб група могла завершитися.
- У `GET /repos/:id/pulls` однією пакетною вибіркою для PR поточного репозиторію та робочого простору підготувати групи, у яких є принаймні один запуск і всі збережені запуски фіналізовані. Для кожного PR вибрати найновішу за часом створення з детермінованим другим ключем. У вибраній групі обчислити суму, кількість відомих сум та кількість запусків. `review_cost_usd` дорівнює `null` за відсутності відомих сум. `review_cost_is_partial` дорівнює `true`, коли відомі деякі, але не всі суми. Група з невідомою ціною залишається вибраною, якщо вона найновіша. Не додавати запит на кожен PR або виклик сервісу тарифів під час читання.
- Сумісні зміни контракту внести в обидві копії `contracts/platform.ts` і `contracts/trace.ts`. Імпорт GitHub і старі відповіді можуть не містити полів вартості. Новий сервер повертає `null` для невідомої ціни. Для історії запланувати необов’язкову ознаку `cost_pending`, щоб клієнт розрізняв фіналізоване `null` та суму, яка ще очікується після скасування.

## 3. Три екрани та оновлення

- **Timeline і Trace.** Додати `Cost` у `RunHistory` під часом запуску поруч із сумою вхідних і вихідних токенів, а в `TraceBody` між `Tokens` і `Findings`. Використати один форматер USD і переклади в поточних `prReview` та `runs`. Перевірити компактну верстку, читання доступних підписів і точність до чотирьох знаків.
- **Pull Requests.** Додати узгоджені клітинки заголовка й рядка біля `Status` у `PullsPage`, `PRRow` та їхній спільній сітці. Для `Partial` показати пояснення, що частина агентських цін невідома. Використати наявне завантаження PR і фільтри.
- **Оновлення.** Після фіналізації та видалення запуску інвалідувати `['pulls', repoId]`, історію та відповідну трасу. SSE закривається після запису остаточного стану. Після запиту на скасування статус може змінитися раніше, тому продовжити опитування історії, доки сервер повертає `cost_pending`. Відкласти доступність видалення до фіналізації й застосувати цю ж умову на сервері. При переході в остаточний стан оновити список і відкриту трасу. Найсвіжіша ціна підтягується після повернення до списку. Для активного списку лишається поточне періодичне оновлення.

## 4. Перевірка доставки

- **Сервер.** Інтеграційні сценарії з моками моделей і реальною БД. Перевірити завершення успіхом, помилки та скасування, активні й паралельні групи, видалення, нуль, повну та неповну суми, старі рядки, однакові номери PR у різних репозиторіях і доступ до трасування в іншому робочому просторі.
- **Клієнт.** Компонентні тести трьох місць відображення, `Partial`, невідомого значення та оновлення відкритого Trace після остаточного збереження. Перевірити колонку та картки у вузькому вікні.
- **Браузер.** Додати до наявного seed два пов’язані запуски зі збереженими цінами `$0.06` і `$0.0013` та придатним до читання трасуванням. Пройти Pull Requests → Agent runs → Trace, звірити `$0.0613` у списку та `$0.0013` у двох місцях для відповідного запуску. Сценарій використовує задані дані й працює без викликів моделей.
